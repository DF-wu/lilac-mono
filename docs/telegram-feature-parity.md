# Telegram Feature Parity

Language: [`English (primary / canonical)`](./telegram-feature-parity.md) · [`Traditional Chinese (translation)`](./telegram-feature-parity.zh-TW.md)

This document compares the fork-owned Telegram surface (`apps/core/src/surface/telegram/`) with the upstream Discord surface (`apps/core/src/surface/discord/`). For every capability Discord has that Telegram lacks or implements differently it records the status, why the gap exists, and what would have to change to close it. It also lists what Telegram has that Discord does not.

The baseline is the Telegram request router rewrite merged as fork PR [#75](https://github.com/DF-wu/lilac-mono/pull/75) (`refactor/telegram-upstream-alignment`, merge commit `8e134266`, 2026-10-05), which made the Telegram router mirror the upstream Discord router. Every claim below was re-checked against the code at that commit; file paths are relative to the repository root, and paths without a directory prefix inside a Telegram or Discord row live under that surface's directory.

> [!IMPORTANT]
> This is a maintenance document, not a roadmap. When a row's capability is implemented, lands upstream in a platform-neutral form, or is dropped as a non-goal, update or remove the row. "Not yet implemented" means feasible, not approved: it is not a work item until a plan says so.

## How gaps are classified

| Class                 | Meaning                                                                                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bot API limitation    | The Telegram Bot API cannot do it. Nothing in this repository can close the gap; where an approximation is possible the row says what it would be                         |
| Deliberate non-goal   | A decision was made not to build it, and the row records the reason                                                                                                       |
| Not yet implemented   | Feasible inside fork-owned modules (`apps/core/src/surface/telegram/`, `packages/utils/core-config/telegram-*.ts`) without changing an upstream contract; simply not done |
| Upstream contract gap | A shared or upstream file hard-codes Discord, so the Telegram implementation needs a contract change first. The row names the file                                        |

## Parity reached by the router rewrite

The Telegram router (`telegram-request-router.ts`, `telegram-request-router-composition.ts`, `telegram-request-router-publish.ts`) now has the same shape as `discord-request-router.ts` and imports the shared helpers under `apps/core/src/surface/discord/discord-request-router/` unchanged (they carry no fork modifications). These are no longer gaps:

| Capability                                         | Telegram implementation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Shared with Discord                                                                                          |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Active request tracking                            | `startTelegramRequestRouter` opens three bus subscriptions: `evt.request` lifecycle keeps one active request per session, `evt.surface` records the bot's output message ids for that request, `evt.adapter` dispatches inbound messages                                                                                                                                                                                                                                                                        | Same topology as the Discord router                                                                          |
| Session modes                                      | `describeRouting` resolves mode, gate flag, model override, and config id through `getSessionMode`, `resolveSessionGateEnabled`, `resolveSessionModelOverride`, and `resolveSessionConfigId`; DMs are always `active` and never gated (`handleActiveDm`)                                                                                                                                                                                                                                                        | `discord-request-router/common.ts`, `surface.router.*` config                                                |
| Debounce batching                                  | `bufferActiveChannelMessage` buffers plain active-mode messages for `surface.router.activeDebounceMs`; `flushDebounce` composes every buffered message into one `prompt` through `composeTelegramMessages({ batch })`                                                                                                                                                                                                                                                                                           | Same config key; composition is Telegram-specific because history comes from the local index                 |
| LLM gate                                           | `shouldForwardByGate` is the default evaluator (the `routerGate` input is a test seam). `evaluateActiveBatchGate` gates active-mode batches and fails closed; `passesDirectReplyGate` disambiguates a reply to the bot that also mentions someone else and fails open                                                                                                                                                                                                                                           | `discord-request-router/gate.ts`, `context.ts`                                                               |
| Steer, interrupt, follow-up, fork, buffered prompt | `routeWhileActive` delegates to `decideActiveRequestRoute`; steer and interrupt first publish `cmd.surface.output.reanchor` through `publishTelegramOutputReanchor`                                                                                                                                                                                                                                                                                                                                             | `discord-request-router/decisions.ts`                                                                        |
| Directives                                         | `!model:` (`parseLeadingModelOverride`), `!continue` (`parseLeadingContinueDirective`), `!interrupt` (`parseSteerDirectiveMode`); `directiveTransform` strips them before the model sees the text                                                                                                                                                                                                                                                                                                               | `discord-request-router/common.ts`                                                                           |
| Mention-mode pending replies                       | Replies to the active output without a mention are queued (`enqueuePendingMentionReply`), flushed as one prompt when the source request settles (`flushPendingMentionRepliesAsPrompt`), or as follow-ups after a steer (`flushPendingMentionRepliesAsFollowUp`); batches are keyed per session and source request (`pendingReplyKey`) and stay queued in memory until their prompt is published, so a failed flush leaves them queued instead of discarding them and a newer active request cannot replace them | Telegram-local implementation mirroring `discord-request-router/pending-batch.ts`                            |
| Custom commands                                    | `commandMetadata` runs before mode dispatch in `routeAdapterMessage`, so `/lilac:<name>` or `/lilac_<name>` works in mention mode without a mention                                                                                                                                                                                                                                                                                                                                                             | Discord uses slash interactions (`discord-command-projection.ts`)                                            |
| Request publication                                | `publishTelegramRequest` emits `cmd.request.message` with `authenticatedOrigin`, `triggerType`, `chainMessageIds`, `participantUserIds`, `sessionMode`, `sessionConfigId`, and `request_client: "telegram"` headers                                                                                                                                                                                                                                                                                             | Same envelope as `discord-request-router/publish.ts`                                                         |
| Reply-wait suppression                             | `shouldSuppressAdapterEvent` lets `waitForReply` reserve a message before routing; a hook failure becomes a routing failure that parks the adapter event (`park-pending`): it stays in the Redis pending-entry list, unrouted and excluded from automatic reclamation                                                                                                                                                                                                                                           | Same hook shape; the Discord router logs `router suppression hook failed; proceeding` and fails open instead |

## Telegram platform features not used

Discord has no equivalent for these, so they are Telegram-side choices rather than parity gaps.

| Feature                       | Status                                                                                             | Why                                                                                                                        | What it would take                                                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Webhook ingress               | Long polling only (`bot.start()` in `telegram-adapter.ts`)                                         | Deliberate non-goal: polling needs no public HTTPS endpoint and works behind NAT; a rival poller surfaces as a fatal `409` | `setWebhook` plus an HTTP route with secret-token verification; a trust-boundary change under `scripts/architecture/README.md` |
| Inline queries                | Not handled                                                                                        | Not yet implemented                                                                                                        | Register `inline_query` in `allowed_updates` and answer with `answerInlineQuery`; results need their own session model         |
| Business accounts             | Not handled                                                                                        | Not yet implemented                                                                                                        | `business_connection` and `business_message` updates plus a business-aware allowlist                                           |
| Voice and video transcription | Audio, video, and voice degrade to `[telegram_attachment …]` markers (`telegram-inbound-media.ts`) | Not yet implemented; a speech-to-text provider is a new dependency and must be approved first                              | A transcription step in the inbound media pipeline                                                                             |

## Telegram capabilities Discord lacks

| Capability                                 | Telegram                                                                                                                                                                                                                              | Discord                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Durable ingress outbox                     | Every update is written to `telegram_ingress_outbox` before publication and replayed oldest-first after a restart (`telegram-ingress.ts`, `store/telegram-surface-store.ts`, `scheduleIngressReplay` in `telegram-adapter.ts`)        | No outbox; gateway events are published directly                                                                           |
| Per-user allowlist                         | `allowedUserIds` gates principals inside an allowed chat (`telegram-guards.ts`); `allowedChatIds` fails closed                                                                                                                        | `allowedGuildIds` and `allowedChannelIds` only                                                                             |
| Polling supervisor                         | `supervisePolling` turns an unexpected exit into a red `telegram.ready` check and classifies `401` and `409` as fatal (`isFatalTelegramPollingExit`)                                                                                  | discord.js reconnect handling; no fatal classification                                                                     |
| Forum topics as sessions                   | `<chat_id>:<topic_id>` session ids let `surface.router.sessionModes` target one topic (`telegram-ids.ts`)                                                                                                                             | Threads are sessions, but there is no forum-topic distinction in the id                                                    |
| Byte-budgeted inbound media                | The adapter implements `SurfaceAttachmentResolver` (`apps/core/src/surface/adapter.ts`); media is resolved from `file_id`, sniffed, capped per attachment and per request, and written to the BlobStore (`telegram-inbound-media.ts`) | Attachments are passed as CDN URL resources                                                                                |
| Live allowlist re-check for workflow cards | `createTelegramWorkflowTargetAuthorizer` (`telegram-surface-runtime.ts`) re-reads `allowedChatIds` before every progress-card send, edit, and recreation, and before a due schedule fires                                             | No per-send authorizer                                                                                                     |
| Self-hosted Bot API                        | `apiRoot` points the client at a local Bot API server                                                                                                                                                                                 | Not applicable                                                                                                             |
| HTML to plain fallback                     | `withFallbacks` in `output/telegram-output-stream.ts` retries a send without `parse_mode` when Telegram rejects the entities                                                                                                          | Not applicable                                                                                                             |
| Command menu size                          | `setMyCommands` publishes up to `TELEGRAM_MAX_MENU_COMMANDS = 100` aliases on every connect                                                                                                                                           | The `lilac` slash command carries at most 24 custom-command options (`customOptions.slice(0, 24)` in `discord-adapter.ts`) |

## Updating this document

After an upstream sync or a Telegram change, re-check the files each class depends on:

- Upstream contract gaps: `apps/core/src/tools/question.ts`, `apps/core/src/surface/bridge/request-composition/checkpoint-selection.ts`, `resolveSafetyMode` in `apps/core/src/tool-server/create-tool-server.ts`, the Discord branch of `apps/core/src/conversation/thread-store.ts`, and the enrichment calls in `apps/core/src/tool-server/tools/surface.ts`. If upstream makes one platform-neutral, the row becomes "not yet implemented" or is removed.
- Shared router helpers: `apps/core/src/surface/discord/discord-request-router/`. The Telegram router imports them unchanged; a signature change there breaks the parity rows above before it breaks tests.
- Telegram behaviour: `cd apps/core && bun test tests/surface/telegram/` covers the router (`telegram-request-router.test.ts`), the outbox, polling supervision, and the adapter against the fake Bot API server.

Keep [`telegram-surface.md`](./telegram-surface.md#10-what-works-and-what-does-not) and the Telegram rows in [`fork-differences.md`](./fork-differences.md) consistent with this table.
